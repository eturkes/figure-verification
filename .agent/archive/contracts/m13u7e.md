# M13.7e — a corpus filename still spells a region code retired two units ago

Tier: **data**. The artifact is one example spec and the four references that name it; every one is
re-validated at use by the committed gate — the corpus digest pin, the example parity sweep, the
eval golden and the index loader — so a defect is re-checked for free by a rerun and fixes forward.

Gate identity: `bash tools/gate.sh`, eight stages, green at 8/8 on a clean tree at the closing
commit, run under both umasks now that the preceding unit made rc umask-independent.

## What this unit decides

`examples/good_specs/g08_na_revenue_by_month.json` filters `region eq "US"` and its digest is
current, but its BASENAME still spells `na` — the region code retired two units ago, first to `NAM`
and then to `US`. The demo-data unit left it stale deliberately and the region-code unit restated
that choice, both correctly: neither had a reason to move a file. The name is now the last carrier
of a code no data, spec or test still holds, and a filename is the one citation form a digest sweep
cannot repair.

User ruling: rename it. New basename `g08_us_revenue_by_month.json`.

## Surfaces

Four references, the census being `/usr/bin/rg -n 'g08_na_revenue_by_month'` over `git ls-files`,
which returns 8 hits of which 4 are live and 4 are archive:

| file | what moves |
|---|---|
| `examples/good_specs/g08_na_revenue_by_month.json` | the file itself, `git mv`, content untouched |
| `examples/index.json` | the `"file"` field of the g08 entry |
| `tests/test_eval.py` | the filename string AND the test FUNCTION name `test_g08_na_revenue_by_month` |
| `tests/test_oracle_parity.py` | the filename in the parametrize tuple |
| `.agent/archive/contracts/m13u7b.md`, `m13u7c.md` | NONE — history; each records the name as it stood, including the region-code unit's explicit decision not to rename it |

ONE downstream pin, and it is the reason this is not a pure `git mv`:
`bench/__main__.py` `_EXPECTED_GOOD_CORPUS_DIGEST`. `_corpus_digest` is NAME-sensitive, not just
content-sensitive — `tests/test_bench_harness.py::test_corpus_digest_is_content_and_name_sensitive`
is the committed proof — so renaming a good-spec file moves that digest even though no byte of
corpus CONTENT changes. `.secrets.baseline` follows, because that constant is a BARE 64-hex literal
and the recorded rule is that the `secrets` stage tracks bare hex while never matching a
`sha256:`-PREFIXED citation.

The bad-corpus digest does NOT move: g08 is a good spec, and the two digests are computed over
separate directories.

## Predicates

**E1 — the file moves with its content intact.** Accept: `git mv` recorded as a pure rename, and the
new path's bytes are `cmp`-identical to the old path's bytes at HEAD.

**E2 — no live reference survives to the old basename.** Accept: `/usr/bin/rg -n
'g08_na_revenue_by_month'` over `git ls-files` returns matches under `.agent/archive/` and inside
this unit's own closing `Phase` record in `.agent/spec.md`, and NOWHERE else. Both classes are
HISTORY and must not move: a rename record cannot describe a rename without naming what was
renamed, which is the same carve-out the region-code unit's own R3 made for a predecessor's closed
`Phase` entry. Positive control: the same sweep for `g08_us_revenue_by_month` returns 5 files —
the 3 live references plus `.agent/spec.md` and this contract. The renamed FILE is not among them
and must not be expected there; a JSON spec does not contain its own basename.

E2 is ORDER-DEPENDENT and that is the trap it was caught by: verified before the closing `Phase`
entry was written, the sweep was true when run and went stale the moment the record describing the
rename introduced a fresh occurrence of the old name. A unit that sweeps for a retired token and
then writes prose naming that token must RE-RUN the sweep after the prose lands.

**E3 — the spec still verifies and still selects the same rows.** The rename must be inert to
meaning. Accept: the renamed spec's 8 checks all return `status: pass`, and its filter selects 3
rows at 12000/15000/13000 — byte-identical outcomes to the pre-rename file, since only the name
moved.

**E4 — the name-sensitive pin is re-pinned, not relaxed.** Accept: the good-corpus digest goes RED
on the first gate after the rename, is re-pinned to a value freshly computed from the tree, and the
BAD-corpus digest does NOT move. The good pin fires ALONE this time, which is itself the evidence
that the masking recorded by the region-code unit was a masking and not a dead assertion: with the
bad assert passing, the good assert is finally reached.

**E5 — the gate is green at 8/8**, run under `umask 0077` and `umask 022`, both rc=0. `.secrets
.baseline` regenerated with NO new finding class: file and finding counts match HEAD and only
`hashed_secret` values move.

## What this unit does NOT do

- It does not touch the spec's CONTENT, its digest citation, its filter, or any other example.
- It does not rename any other corpus file. No other basename carries a retired code — the sweep
  that found this one returns nothing else.
