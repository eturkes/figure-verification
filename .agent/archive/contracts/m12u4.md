### V3 — what was proven and what was not

**Proven, live on the host of record.** `POST /propose-spec {"user_request":"Plot a scatter chart of
revenue versus orders.","dataset_name":"sales.csv"}` → **HTTP 200 in 106.9 s**. The real dGPU model
emitted a well-formed guided `vplot-0.1` document binding the correct dataset digest
(`sha256:76356beb…`); the verifier ran **8 checks, 7 pass, 1 blocking fail** and returned
`verified=false`, `plot_id=null`:

    encoding.fields_exist_in_plotted_table | deterministic_recompute | fail | blocking
      channel field(s) ['month', 'region'] absent from plotted columns ['orders', 'revenue']

That is the project's thesis executing live on CURRENT: the untrusted proposer proposed, its own
transform and encoding disagreed, and the trusted verifier blocked it deterministically. It is ONE
draw and therefore an OBSERVATION of one `(device, config)` tuple — never a rate, never a bound, and
NOT an input to M10's ≥70%/≥70% acceptance, which is corpus-measured.

In the browser, additionally proven: sign-in, the chat surface, the header reading
`Qwen2.5-Coder-0.5B-Instruct`, and 1 registered tool server.

**Not proven.** A chart rendering INLINE from a browser-typed prompt. Cause is the automation layer,
not the stack: in this BrowserOS build `snapshot` returns an empty tree with no refs for the OWUI
SPA, `run` swallows both its return value and `console.log`, and `click_at` never focuses the
composer at either 1:1 or /2 coordinate scaling, so `type` lands nowhere. Keyboard-only events DO
dispatch (Tab+Enter completed the login, Escape closed the release-notes modal). M12.4b owns this
arm and must first settle a working browser route (a `webcap`/CDP path, or OWUI's own
`/api/chat/completions` with the operator token to drive the filter leg headlessly).
