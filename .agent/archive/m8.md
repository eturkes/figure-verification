## Memory notes — M8 (schema-guided decoding)
- Schema-guided decoding is the shipped DEFAULT, measured on the live NPU (`Qwen2-0.5B-Instruct-int4-sym-ov`, greedy `temp=0`, `n=100` HTTP-200 verdicts, reproducible per (device,config); reports gitignored). The same-commit A/B (`2b4fa60`, `git_dirty=false` in BOTH arms, identical verifier/prompts/model/device, ONLY `MODEL_BACKEND_STRUCTURED_OUTPUT` flipping) isolates guidance as the sole variable: `verified_render` RAW `0/100` → GUIDED `26/100`; `json_validity` `0.01→0.83`; fenced `52→0`, bare_object `47→100`, de-fenced-valid `13→83`; buckets `schema` `1.00→0.51`, `semantic` `0.00→0.23`. The shipped default run reports that same 26/100 with `spec.decode`(51) + `encoding.fields_exist_in_plotted_table`(22) on top, so the residual splits between token-cap/value-level strict-decode failures and semantic blocks no schema can enforce. The wider historical 0→26 comparison also spans the M5.1h generation-path fix (`548809e`) and the M5-M7 verifier evolution → cite the A/B for attribution. Guidance adds NO trust: the strict verifier still re-decodes, recomputes, and re-binds the CSV SHA-256, and the guarantee held IDENTICALLY in both arms (18/18 bad blocked, 10/10 good accepted, 0 transport faults). `verified_render` counts VERIFIER passes, never prompt-intent satisfaction (a spec can verify while not answering the request); every rate here is an observation, not a bound. Arms self-document in their reports (`backend.structured_output=false` + schema `null` versus `true` + `sha256:2bab7c6…`); run recipe + the `--model-url`-vs-`VERIFIER_MODEL_BASE_URL` caveat = `bench/README.md`.
- OP-GOTCHA (A/B runs): `model_backend` self-`setsid`s at startup (own PID=PGID=SID, reparented off the launcher) → an EXIT-trap `kill -TERM -<launcher-pgid>` LEAKS the server, which keeps squatting :8001; reap by the PID actually bound to the port (`ss -ltnp … :8001`), never the launcher's process group.
- OpenVINO GenAI 2026.2.1 xgrammar rejects negative-lookahead `pattern`; `Engine.load` derives guidance once from the authoritative VPlot schema by stripping `pattern`/`format` when `settings.structured_output` is enabled, and missing/unreadable/invalid schema fails closed. `Engine.generate` applies `StructuredOutputConfig` only when its per-request `guided` flag is true; guidance constrains structure only, while strict verifier re-decode, semantics, and provenance remain authoritative. `ChatCompletionRequest.guided_json` defaults false and `chat_completions` threads it; verifier `propose_spec` sends true, while OWUI/generic traffic omits it and stays unconstrained—global guidance made plain `capital of France?` chat emit VPlot JSON, motivating request scoping. Split = convention, not hard boundary: OWUI `apply_params_to_form_data` promotes any non-null param to the outbound root with no `guided_json` allowlist → 6 latent injection paths (root field / `params` / `custom_params` / persisted + global model params / an inlet filter), all inactive in the shipped clean snapshot; a leak only re-triggers the plain-chat UX regression, never a false verification (guidance adds no trust).
- Live OWUI (real NPU, greedy): its two-call flow first uses unconstrained model tool selection, then only a selected `proposeSpec` invokes request-guided generation. An explicit `dataset_name: sales.csv` cue is required for a well-formed tool call; loose `from/using sales.csv` drops the argument (400) or goes straight to matplotlib. Once called, schema guidance makes OWUI's reformulated request verify (the direct semantic-fail does not reproduce), so the blocked path is model bypass → raw chart → guard. `run_persisted_chat`/`_completed_chat_result` reads `output[0].content[0].text`; background replies leave legacy `content=""`, so the outlet must inspect/rewrite `output[]` and assign a NEW deep copy—OWUI `outlet_filter_handler` (`middleware.py` ~L3336/~L3396) persists only when `message["output"] != original_message["output"]`. Pinned prompts: `Plot a scatter chart of revenue versus orders. dataset_name: sales.csv` → verified `chart/519a22ee...`; the blocked pin = an extravagant multi-panel `Build a fancy sales.csv dashboard: a 2x2 grid of subplots ...` (VPlot-inexpressible + cues the fenced matplotlib the guard catches; wired, exact greedy reply on the current device/config unconfirmed). RULE: a "blocked" demo prompt must reliably elicit a chart SIGNAL (fenced matplotlib/plotly/altair/seaborn, `<svg>`, vega-lite JSON, `data:image`) — a prose refusal (`as an AI language model, I don't have access to specific data or datasets`) carries none, so the guard passes it through UNBLOCKED. Persisted-chat reader (`_completed_chat_result`) is POSITIONAL (`output[0].content[0]`) — correct for the single-`content`-item `model_backend` reply (Qwen2-0.5B, no reasoning item), fragile against a reasoning-capable backend prepending a `type="reasoning"` item (would return reasoning text or reject the chart chat as no-final-text, dropping the blocked notice); `enforcement_filter` likewise concatenates all `output[].content[].text` with no type check → Deferred (inert under the shipped backend).
- Verified-chart CLOSING LINE (demo UX): OWUI's legacy-FC loop re-prompts `model_backend` for a human-facing final answer AFTER the verifier certifies+embeds the chart (OWUI str()-ifies the verifier success summary into that turn's `<source>` citation context per the rich-embed contract) → the 0.5B proposer emits unrelated filler (observed: a fabricated `increases efficiency by 20% [1]` study citation). `model_backend/verified_chart.py` recognizes that ONE turn and returns a fixed `VERIFIED_CHART_REPLY` (`Figure Verifier confirmed the chart; all checks passed.`) WITHOUT generating. Detection = the verifier summary shape `Verified chart for {dataset}: all {N} checks passed.` (regex `Verified chart for .+?: all \d+ checks passed.`) present in any request message; the summary exists only POST-verification, so it never appears in the tool-selector turn (`Available Tools:`), the verifier's own guided spec-generation turn (`You are proposing a VPlot v0.1 chart specification.`), or ordinary chat — those still run the model (`chat_completions` short-circuits only when `is_verified_chart_summary` is true). Wire contract, NOT an import (the untrusted proposer stays decoupled from the verifier; match the summary, not OWUI's `<source>` wrapper, so recognition survives OWUI changing that wrapper). Cosmetic-only: spec proposal + every verifier guarantee untouched, and the verifier re-decodes/re-verifies every real proposal regardless (a crafted user message echoing the summary just gets the canned line, harmless in a demo backend). `VERIFIED_CHART_REPLY` is the single source of truth shared with the stub's `_FINAL_REPLY` (`webui/model_stub.py` imports it — hardware-free, no openvino) so live NPU + stub close the demo identically; the stub reaches it as its scripted fall-through, the live backend via the summary gate. `model_backend/app.py` factored a shared `_completion` envelope helper across the canned + generated paths (reports `settings.model_name`, word-count-proxy usage on the canned path). model_backend coverage-excluded → tests are regression-only (`tests/test_model_backend.py`: pure classifier cases + a TestClient short-circuit asserting `generate` never runs).
