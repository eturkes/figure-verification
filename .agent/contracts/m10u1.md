# M10.1 — the outlet filter authors the verdict on BOTH paths

Tier **kernel**: the filter is the one surface that decides what a user SEES, and no downstream
re-check exists — a false PASS publishes an unverified figure, a false FAIL hides a verified one.
Gate identity `bash tools/gate.sh`. Dispatch: `test` (diff-blind red suite from these predicates) +
`orc` (independent implementation of the publication decision → differential) + `prod`
(implementation + mutation credit + the live witness); MAIN holds the primary tree + gate and
writes the law prose (`.claude/rules/owui.md`, `.agent/spec.md`). Builds on the M10.4 tool (formula
candidate) — implementation starts from the commit that closes M10.4.

## What this unit ships

1. **The receipt** (`webui/paste_in/receipt.py`, NEW): the tool writes plain data about the call it
   received to backend-owned request state; the tool's return string stays one of `TOOL_VERDICTS`.
2. **The filter** (`webui/paste_in/filter.py`, NEW) = the SECOND paste target: an async outlet that
   re-derives the verdict from the receipt, runs the verified program in the user's Pyodide sandbox
   through a direct `execute:python` RPC, and rewrites the reply to exactly one verdict.
3. **Packaging + demo wiring**: `ARTIFACTS` gains `paste-in/figure_verification_filter.py`;
   `webui/enforcement_filter.py` + its tests retire; bootstrap provisions the generated filter as the
   one global active outlet; `webui/settings.py` sets `BYPASS_EMBEDDING_AND_RETRIEVAL=true`;
   `webui/model_stub.py` gains a deterministic `draw_figure` tool call for the live witness.

## Rulings restated

- `Intent` + ruling 4: pass ⇒ inline PNG + `Figure verification passed`; fail ⇒ blocked +
  `Figure verification failed, no image produced`. Verification model tier 3: the certificate
  publishes what was verified in plain words ⇒ the PASS text carries `certificate.interpretation`.
- M10 ruling 1 (transport): only an authentic backend-recorded tool call may publish a figure; a
  fenced program in the reply is not a publication path. M10 ruling 2: CSV bytes come from OWUI
  storage in-process, ownership-checked. M10 ruling 3: TWO generated files, one per paste target.
- Ruling 1: the model authors the EXECUTED bytes — the sandbox runs the receipt's program verbatim;
  the filter's wrapper is trusted code around those bytes, never a rewrite of them.
- Ruling 5: the verifier alone decides; the filter adds no pass/fail rule of its own beyond
  withholding when the render itself fails. Ruling 6: no admission vocabulary in model-facing bytes
  (the tool docstring + `TOOL_VERDICTS` stay byte-unchanged).
- Measured mechanism (spike-m10-1, scratch, OWUI 0.10.2): the tool and the outlet of ONE completion
  share one `__request__` object in native AND legacy function calling; ONE outlet call per
  completion (no `/api/chat/completed` in normal flow); `__event_call__({'type': 'execute:python',
  'data': {'id', 'code', 'session_id', 'files': [{'id', 'filename'}]}})` returns `{stdout, stderr,
  result}` with the CSV at `/mnt/uploads/<filename>` byte-identical to the upload; OWUI's own
  `patchMatplotlib` fires on the substring `matplotlib` and raises `SyntaxError` before the program
  runs; rewriting `content` AND `output` persists across reload; a `files` event persists the PNG as
  an attachment; RPC wall time 9.2–12.0 s; the inbound Engine.IO frame cap is 1,000,000 bytes;
  `__files__`/`__metadata__['files']` are conversation-scoped, not turn-scoped; an offline CSV upload
  calls a remote embedding API unless `BYPASS_EMBEDDING_AND_RETRIEVAL=true`.

## Invariant surfaces

- `src/verifier/**` byte-unchanged (the filter embeds the core; it never edits it).
- The tool docstring, `TOOL_VERDICTS`, and every model-facing byte stay free of the banned stems.
- The executed program = the receipt's program, byte for byte (F6).
- Gate rc=0, 8/8, 100.00% branch over `verifier`, under `umask 022` AND `umask 0077`.

## Amendments

### A1 — seams (lead ruling, before dispatch)

The diff-blind suite, the oracle and the implementation bind exactly these names; every other
internal stays the implementation's.

- `webui/paste_in/receipt.py`: `Receipt(program: str, file_ids: tuple[str, ...], request_text: str | None)`,
  a frozen slotted dataclass; `RECEIPT_ATTR: Final = "figure_verification_receipt"` = the attribute
  on `__request__.state`; `write_receipt(request: object, receipt: Receipt) -> None`;
  `read_receipt(request: object) -> Receipt | None` = `None` for a missing request, state or
  attribute, and for a value that is not a `Receipt`.
- `webui/paste_in/selection.py` (NEW) holds F3's ONE shared function:
  `first_verdict(program: str, attachments: tuple[UploadedFile, ...], request_text: str | None) -> tuple[Verdict | None, UploadedFile | None]`
  = the verdict + the attachment it consumed (`None` on the formula arm and when no candidate
  exists); candidate order + the `target_mismatch`-only continuation = M10.0's T2-1 + M10.4's T7-T10.
  `tool.py` and `filter.py` each bind it by `from webui.paste_in.selection import first_verdict`;
  the identity pin = `tool.first_verdict is filter.first_verdict is selection.first_verdict`.
- `webui/paste_in/owui_files.py`: `UploadedFile(file_id: str, path: str, content: bytes)` — `file_id`
  = the store id the RPC `files` entry carries; NEW `owned_files(file_ids: Sequence[str], user_id: str) -> tuple[UploadedFile, ...]`
  = F3's re-fetch (order kept; a missing, foreign or unreadable id dropped);
  `uploaded_files(metadata, user_id)` = `owned_files(attachment_ids(metadata), user_id)`.
- `webui/paste_in/tool.py`: `draw_figure` gains `__request__: object | None = None`; the docstring and
  `TOOL_VERDICTS` stay byte-unchanged.
- `webui/paste_in/filter.py`: `class Filter` with `async def outlet(self, body: dict, __user__: dict | None = None, __request__: object | None = None, __event_call__: Callable | None = None, __event_emitter__: Callable | None = None, __metadata__: dict | None = None) -> dict`;
  `PASS_TEXT: Final = "Figure verification passed"`, `FAIL_TEXT: Final = "Figure verification failed, no image produced"`,
  `RPC_TIMEOUT_SECONDS: Final = 60`; `wrapper_code(program: str) -> str` = F6/F7's sandbox source.
  F5's interpretation = `Verified.certificate.interpretation` of the filter's own re-derived verdict.
- Tests fake `open_webui` the way `tests/test_paste_in_tool.py` does: modules injected into
  `sys.modules`, the same call chain driven.
- **A2 (lead ruling on a test-m10u1-1 question, F8 smoke seam + deletion scope).** Smoke reads
  functions through ONE new client seam: `webui/client.py` `FunctionReadback(NamedTuple)` =
  `(id: str, type: str, is_active: bool, is_global: bool, content: str)`, and
  `WebUIClient.function_states() -> tuple[FunctionReadback, ...]` (one element per function the
  instance holds, `content` from the per-id GET), added to bootstrap's `_Provisioner` protocol.
  `SmokeResult` gains three REQUIRED flags: `filter_current` (the `FILTER_ID` element's `content` ==
  the generated filter artifact's bytes), `filter_global_active` (that element `is_active` and
  `is_global`), `filter_exclusive` (the ids of every element with `type == "filter"` and
  `is_active` == exactly `{FILTER_ID}`); any false flag fails bootstrap closed, as the five M10.0
  flags do. Deletion scope: a test that imports `webui.enforcement_filter` only for filter source
  bytes while testing client transport or bootstrap behaviour is REPOINTED to the generated filter
  artifact, not deleted; a test of the one-path filter's own behaviour is deleted.
- **A3 (lead ruling on a prod-m10u1-1 finding, F1 carrier across artifacts).** Each generated
  artifact embeds its own copy of `receipt.py` in an isolated module namespace (B5), so the tool
  artifact's `Receipt` class is not the filter artifact's: a nominal `isinstance` read fails every
  live PASS. The value at `__request__.state.figure_verification_receipt` is therefore BUILTIN plain
  data, identical across artifacts: the tuple `(RECEIPT_TAG, program, file_ids, request_text)`,
  `RECEIPT_TAG = "figure-verification-receipt/1"`. `write_receipt(request, receipt)` stores that
  tuple built from a `Receipt`; `read_receipt(request) -> Receipt | None` returns a `Receipt` only
  for `type(value) is tuple`, length 4, `value[0] == RECEIPT_TAG`, `type(program) is str`,
  `type(file_ids) is tuple` with every element `type(e) is str`, and `request_text` `None` or
  `type(request_text) is str`; any other value ⇒ `None` ⇒ FAIL. No class fingerprinting:
  authenticity rides the channel (backend request state), never the value's type.
